一句话讲清这个工作流

把客户从官网表单、白皮书、直播等渠道来的留言 + 画像 + 行为，在 30 秒内自动打完分、分好级（SQL / MQL / 无效），并替销售把第一句跟进话术写好 —— 分数每一分都能追溯，话术每句话都有知识库出处。

一、工作流全景与 13 节点速查

整条链路是一条主干 + 三路出口。主干按"能规则化的绝不给模型"的原则分工：属性、行为、合分、分级全部用代码节点（确定性、零成本、可审计），只有非结构化的自然语言理解交给大模型。

13 节点速查表

#节点类型作用（一句话）
1start 开始输入收 6 个字段：公司名、留言原文、行业、规模、岗位、行为轨迹
2extract 结构化提取LLM把留言原文洗成 JSON（核心诉求 / 关键词 / 联系方式）
3rules 规则评分器代码算属性分（0-45）+ 行为分（0-25），并输出可读明细
4intent_llm 意图评分LLM读留言判断意向强度，给 0-30 分 + 意图标签 + 理由
5parse_intent 意图解析代码从模型输出里抠 JSON，解析失败自动兜底
6total 总分汇总代码三项相加，按 60 / 30 划出 SQL / MQL / 无效
7branch 分级分流if-else按等级把线索路由到三条完全不同的处理链
8retrieve 产品知识检索RAG用留言原文检索知识库，取最相关 3 段
9advice 跟进建议生成LLM结合检索结果输出四段式跟进建议（含 80 字开场话术）
10nurture 培育内容生成LLM低意向线索生成"推什么资料 + 发什么文案 + 下次何时跟"
11end_sql 结束(SQL)输出回传总分、等级、意图标签、跟进建议
12end_mql 结束(MQL)输出回传总分、等级、培育方案
13end_invalid 结束(无效)输出回传总分、等级、过滤理由

连接关系（对着画布能一眼找到）

start → extract → rules → intent_llm → parse_intent → total → branch，然后 branch 分出三路：true(≥60) → retrieve → advice → end_sql；case_2(≥30) → nurture → end_mql；false → end_invalid。共 12 条连线。

二、逐节点拆解

每个节点按"干什么 → 怎么配 → 为什么这么设计"三段讲。面试时只需要讲清楚这一段，就足以证明你是"搭过"的人，而不是"看图说话"的人。

阶段①：采集与提取

01开始start输入节点

整个工作流的入口。它不是简单的"表单"，而是把线索拆成了三类信息：静态属性（行业/规模/岗位）、行为轨迹、非结构化文本（留言）。这个字段设计本身就是项目最值钱的部分 —— 因为后面的评分维度完全由它决定。

  • 必填留言原文 lead_raw（2000 字）、行业 industry、公司规模 company_size、岗位 job_title（均为下拉）
  • 选填公司名称 company（64 字）、近期行为 behaviors（顿号分隔文本）
  • 选项枚举行业 7 类（含"学生个人"专门作负分项）；规模 5 档；岗位 5 类

设计理由：行业/规模/岗位做成下拉而不是自由文本，是为了让下游代码节点能用字典精确匹配打分 —— 如果让用户随便填"做软件的""互联网公司"，规则引擎就没法稳定命中。这是"为下游服务的输入设计"，面试时值得主动讲。

02结构化提取extractLLMtemperature 0.2

客户留言是最脏的数据 —— 有人写"想了解下"、有人写"我们 CRM 想嵌 AI 评分，支持 API 吗"。这个节点把一段自由文本洗成标准 JSON：need_summary（核心诉求，≤30 字）、need_keywords（最多 5 个关键词）、contact（联系方式或 null）。

  • 输入{{#start.lead_raw#}} 原始留言
  • 提示词约束"仅输出 JSON，不要输出任何其他内容"+"只依据留言原文提取，禁止编造"+"数字、产品名保持原样"
  • 模型gpt-4o-mini，temperature 0.2

设计理由：把"理解人话"和"做判断"拆开。提取节点只负责忠实转写（不判断、不打分），这样一旦下游分数不对，能明确区分是"没读懂"还是"规则不合理"，方便定位问题。

阶段②：双引擎打分（这套设计的心脏）

03规则评分器rules代码节点属性 45 + 行为 25

用一段 Python 把"行业 + 规模 + 岗位 + 行为"翻译成分数。这是全部评分里最需要向客户解释清楚的部分，因为它直接决定了销售信不信这个分数。

  • 行业分软件/互联网 15、金融 12、制造业 10、医疗 10、教育 5、学生个人 -20
  • 规模分500 人以上 15、100-499 人 12、20-99 人 8、1-19 人 5、个人/无 -5
  • 岗位分IT 负责人/技术总监 15、采购/商务负责人 12、销售/市场负责人 8、普通员工 3、学生 0
  • 属性分三项相加后 clamp 到 0~45（防止单项极值把总分带偏）
  • 行为分打开报价邮件 15、预约产品演示 15、观看演示视频 12、访问集成对接页 10、一周内多次访问官网 10、下载白皮书 8；按顿号/逗号切词累加，封顶 25
  • 同时输出attribute_detail / behavior_detail 两串人类可读明细，如"行业[金融]: +12；规模[500人以上]: +15；岗位[采购/商务负责人]: +12"

设计理由有三层：① 可解释 —— 销售看到的不只是"72 分"，而是"这 72 分是怎么来的"，不服可以申诉；② 零成本零波动 —— 确定性判断交给代码，同样的输入永远得同样的分，不消耗 token；③ 可调 —— 权重和阈值都是显式字典，客户说"我们金融行业最好跟"改一个数字就行，不用重训模型。

04意图评分intent_llmLLMtemperature 0.2

留言里"想了解下"和"支持 API 对接吗"含金量差十倍，这个差别只有语义理解能抓。节点从资深销售视角给留言打 0-30 分，并给出意图标签和一句话理由。

  • 六档评分标准（直接写在提示词里）集成/嵌入/API/iframe 对接 25-30 ｜ 问报价费用 22-28 ｜ 约演示/申请试用 18-24 ｜ 问功能细节 10-16 ｜ 泛泛了解 0-6 ｜ 其他一般咨询 7-12
  • 意图标签集成需求 / 价格咨询 / 演示试用 / 技术咨询 / 一般了解 / 随便看看（六选一，供后续分群统计）
  • 输出intent_score + intent_tag + reason（评分理由）

设计理由：这是规则做不了、模型最擅长的部分 —— 一词之差就跨越了 20 分。把评分标准写死在提示词里（而不是让模型自由发挥），是为了让分数可复现、可解释，本质上是"用提示词实现了一套软规则"。

阶段③：解析与汇总

05意图结果解析parse_intent代码节点工程健壮性

大模型输出不稳定是常态：可能裹在 ```json 里、可能前面加一句"好的，分析如下"。这个节点用正则 \{.*\} 把 JSON 抠出来解析，解析失败就兜底返回 8 分 + "一般了解" + 说明文字，绝不让主流程报错崩溃。

  • 兜底值score=8, tag='一般了解', reason='未解析出JSON，按一般咨询兜底'
  • 二次保险解析出的分数再 max(0, min(30, score)) 强制夹紧到 0-30
  • 理由截断reason[:80]，防止模型啰嗦撑爆输出

设计理由：这 12 行代码是整个工作流的"安全气囊"。POC 演示最怕现场翻车 —— 模型偶尔抽风返回一段散文，没有这个节点整个流程就断了；有了它，最坏情况只是这条线索降级为"一般了解"（进 MQL 培育池），业务不中断。这是能体现工程思维的细节，面试一定要主动讲。

06总分汇总total代码节点60 / 30 阈值

三段分数合体，按两条线划成三个等级。整个工作流的"判决书"就是这 8 行代码。

  • 合分total = round(属性分 + 行为分 + 意图分)，满分 100（45+25+30）
  • 分级≥60 → SQL（销售立即跟进）｜≥30 → MQL（进培育池）｜else → INVALID（自动过滤）
  • 输出total_score + grade

设计理由：把阈值放在代码里而不是让模型"判断这条线索值不值"，是因为概率模型不适合做确定性裁决。阈值可审计、可回归测试、可按客户业务调整 —— 这句话在客户面前极有分量。

阶段④：分级分流

07分级分流branchif-else

一颗三岔路口。三个出口分别接三条完全不同的处理链 —— 这是"分级"真正产生业务价值的地方：不是打个标签就完了，而是不同等级的线索走不同的自动化动作。

  • 分支 1（true）total_score ≥ 60 → 走 retrieve → advice → end_sql
  • 分支 2（case_2）total_score ≥ 30 → 走 nurture → end_mql
  • 分支 3（false）其余 → 直接 end_invalid

设计理由：成本控制点。无效线索不会触发知识库检索和话术生成（省下 1 次向量检索 + 1 次大模型调用）。按 300 条/日的量级，约 77% 的线索被拦在这里，token 花在真正值得跟的客户身上。

SQL 支线：把"高分线索"变成"销售能直接用的弹药"

08产品知识检索retrieveRAG 知识库

在这条线索被确认是高价值之后，才去查资料 —— 用客户留言原文当查询词，从知识库里取最相关的 3 段内容，喂给下游生成节点当"事实依据"。

  • 查询词{{#start.lead_raw#}}（原始留言，不是提取后的摘要）
  • 检索配置multiple 模式、top_k=3、rerank 关闭、score_threshold 为空
  • 知识库3 份文档：《产品功能手册》《常见问题 FAQ》《客户案例集》
  • 注意DSL 里 dataset_ids 为空 —— 导入后必须手动绑定知识库，否则这个节点取不到内容

设计理由：这是防幻觉的第一道闸。话术里但凡涉及产品能力、报价口径，都必须来自检索到的资料，而不是模型的记忆。用留言原文而非摘要做查询词，是因为原始表述里的"API""集成"等词才是向量匹配的关键信号。

09跟进建议生成adviceLLMtemperature 0.4

把"这条线索是谁、想干什么、为什么分高"打包给模型，输出销售可以直接复制粘贴的四段式跟进建议：客户痛点 / 核心需求 / 沟通重点 / 开场话术（80 字以内、口语化）。

  • 上下文注入context 开关打开，绑定 retrieve.result —— 知识库内容进入提示词
  • 输入变量公司/行业/规模/岗位、留言原文、核心诉求、意图标签+理由、属性明细、行为明细
  • 防幻觉指令"优先依据知识库资料回答；资料未覆盖的功能点，明确写'需与产品团队确认'，禁止编造"
  • 禁止空话"必须回应客户留言中的原始诉求，禁止空话"

设计理由：这段提示词是整个项目里最像"售前老手"的地方 —— 它同时解决了三个输出质量问题：不编造（约束来源）、不跑题（必须回应原始诉求）、不像机器（80 字口语化开场话术，销售能直接用）。温度调到 0.4 是为了让话术有点人味但不失控。

11结束(SQL)end_sql输出节点

SQL 支线的出口，回传 4 个字段：total_score、grade、intent_tag、followup_advice。这 4 个字段就是一条可以推给销售的企业微信/CRM 卡片的内容。

MQL 支线：不硬推，先养着

10培育内容生成nurtureLLMtemperature 0.5

意向还不够热的线索，硬推销只会把人推跑。这个节点输出三行培育方案：推荐资料（行业案例 / 白皮书 / 落地视频 选一类）、触达文案（60 字以内，亲切专业不硬销）、下次触达建议（时间 + 内容）。

  • 输入客户公司 + 行业 + 核心诉求 + 意图标签（不带知识库上下文，省成本）
  • 温度0.5 —— 全流程最高，需要文案有变化、不重复
  • 出口end_mql 回传总分、等级、nurture_plan

设计理由：SDR 培育逻辑的自动化。低意向线索的正确处理不是"跟"也不是"丢"，而是"持续给内容、等他自己长大"。把培育动作也交给 AI，就把销售从"发资料"这种低价值重复劳动里解放出来了。

无效支线：果断减负

13结束(无效过滤)end_invalid输出节点

总分低于 30 的线索（典型：学生、竞品调研、随便看看）在这里被拦住，回传总分、等级和filter_reason（过滤理由，取自意图评分的理由字段）。不做检索、不生成任何话术，直接归档。

设计理由：无效线索占总量的大多数，让它们不进入任何付费调用，是这套 POC 成本可控的关键。同时保留 filter_reason 让过滤可复盘 —— 万一误杀了真客户，能查出是哪条规则判错了。

三、五个设计精髓

这五条是"技术选型的理由"，也是面试官必然会挖的地方。客户可能听不懂节点，但一定听得懂这五句话。

精髓 1｜规则与大模型分工：能规则化的，绝不给模型

行业、规模、岗位、行为轨迹是结构化、有限枚举的判断，用代码做：零成本、100% 可复现、永远可解释。留言意图是非结构化语义理解，规则写不完（"想嵌一下"、"有没有开放接口"、"能不能接我们自己的系统"都是一个意思），交给模型。

客户话术

"我们没有让 AI 去猜所有事情。能算准的我们用规则算，算得又快又便宜还能查账；只有'客户这句话到底什么意思'才交给 AI —— 这就是为什么我们敢承诺分数可解释。"

精髓 2｜三段式可解释评分：分数是"论述题"，不是"判断题"

每条线索的分数都能拆回明细：属性分（谁的画像）+ 行为分（干了什么）+ 意图分（说了什么）。销售看到的不是"AI 说这条 72 分"，而是"金融行业 +12、500 人以上 +15、采购负责人 +12、上周打开过报价邮件 +15、问的是 API 集成 28 分"。

客户话术

"销售最怕的是 AI 给个黑箱分数。我们把分数拆成明细摆在销售面前，他不同意可以申诉，我们拿申诉数据反过来校准规则 —— 这套闭环比追求 95% 准确率更重要，因为只有销售信了，系统才用得起来。"

精髓 3｜解析兜底：让模型的不稳定不变成系统的不可用

大模型输出格式漂移是工程事实。工作流里专门放了一个"意图结果解析"代码节点，正则抠 JSON + 失败兜底 8 分 + 分数夹紧，保证任何情况下主流程都能走完并给出结论。

客户话术

"大模型偶尔会不按格式输出，这很正常。我们的设计是：它不听话，系统也不会崩，最坏就是这条线索降级进培育池，不会出现销售那边等不到结果的情况。"

精髓 4｜RAG 防幻觉：话术必须有出处，没有就说不确定

三段防线：① 生成前先检索知识库（3 份文档：功能手册 / FAQ / 案例集）；② 检索内容通过 context 注入提示词；③ 提示词明确要求"资料未覆盖的写'需与产品团队确认'，禁止编造"。

客户话术

"AI 写的话术里涉及的报价和功能，都是从你们自己的产品文档里检索出来的。文档里没有的，它会写'需与产品团队确认'，而不是编一个数字 —— 在售前场景里，一句错承诺的代价比少写一句话大得多。"

精髓 5｜成本与温度的分层设计

成本上：条件分支前置，约 77% 的线索（无效）不触发检索与话术生成；MQL 支线不注入知识库上下文。温度上：提取 0.2、意图 0.2（要稳定可复现）、建议 0.4（要人味）、培育 0.5（要变化）。同一套工作流里，什么任务用什么参数，是明确设计过的。

客户话术

"不是每条线索都值得花一次大模型调用。我们让系统先把 70% 没价值的线索免费筛掉，钱花在真正值得跟的客户身上 —— 这也是为什么这套方案的单条处理成本能压到很低。"

四、客户侧话术包

4.1 三分钟演示脚本（照着走）

步骤动作你要说的话
0:00开场，不打开系统"先问一个问题：您这边市场部每天收到多少条线索？是销售一条条看，还是系统帮您挑？"（等对方说，然后接）"我们今天不做概念介绍，直接现场跑三条真实类型的线索给您看。"
0:30跑用例 1（SQL）"苏州一家设备制造企业，IT 负责人留的言：'旧 CRM 想嵌 AI 评分，支持 API 对接吗？' —— 注意看，系统给了 72 分，判成 SQL。这个分不是拍的：软件/制造行业 10 分、500 人以上 15 分、IT 负责人 15 分、上周打开过报价邮件 15 分、问的是 API 集成 28 分。"

2:15跑用例 2（MQL）+ 用例 3（无效）"换成杭州一家电商公司的普通员工，留言'先了解一下功能' —— 45 分，MQL，系统不硬推，给了一条培育方案：推什么资料、发什么文案、什么时候再跟。再看第三条，学生留言'写作业需要了解 CRM' —— 12 分，直接拦掉，不占用任何资源。三条线索，三种动作。"
3:00收尾抛问题"您现在的流程里，从客户留资到销售第一次联系上，平均要多久？"（对方答"一天以上"）"这套跑完不超过 30 秒，而且第一句话已经写好了 —— 我们现在缺的只是您这边的真实数据，做两周回测把分数线校准到您的业务习惯上。"

4.3 必须主动讲的五条边界（讲清边界反而更可信）

  1. 数据依赖：行为轨迹（预约演示、打开报价邮件等）依赖埋点与渠道回传，接入前要先确认客户 CRM/表单能不能给出这些字段。给不出，就只剩属性分 + 意图分（满分 75）。
  2. 阈值需要校准：60/30 是初始值，必须用客户近 6 个月的成交/流失线索回测 2-4 周后才能定稿。不要承诺"开箱即准"。
  3. 幻觉边界：话术中的产品参数以知识库为准，未覆盖的内容会输出"需与产品团队确认"，不能直接对外承诺。
  4. 合规边界：客户留言与个人信息仅用于本条线索跟进，需在隐私政策中声明；不做跨客户数据训练。
  5. 平台依赖：Coze/Dify 版本迭代可能影响节点行为，重大升级前需回归测试。

五、面试追问 12 问

每一问都按"先给结论，再给理由，最后给一个细节"的结构答。最后那个细节才是拉开差距的地方。

Q1为什么不让大模型直接打总分，非要拆成规则 + 模型？

结论：因为只有一部分判断适合模型。理由：行业、规模、岗位、行为是有限枚举的确定性判断 —— 用代码算，成本是 0、结果 100% 可复现、还能输出明细供销售申诉；模型打分会有随机性，同一线索两次跑出不同分，销售就不信了。细节：你看我的规则节点里特意做了 clamp(0,45) 和 min(25) 封顶，就是防止某个单项极值把总分带偏 —— 这类边界处理是"想清楚了"和"跑通了"的区别。

Q260 / 30 这两条线是怎么定的？

结论：POC 阶段是经验初始值，不是算出来的，必须回测校准 —— 这一点我从不粉饰。理由：当时没有客户的真实成交样本，我按"满分 100 分、SQL 需要画像好 + 有强行为 + 强意图同时成立"的常识设了 60；30 是"至少有一项明显正向信号"。细节：校准方法是拿客户近 6 个月已成交和已流失的线索做回测，看不同切分点下的精确率/召回率取舍 —— 业务上宁可漏掉也不能误杀（漏掉的还能培育回来，误杀的客户就丢了），所以阈值会偏向"宁松勿紧"。

Q3大模型输出格式不稳定怎么办？

结论：三层防护，缺一不可。理由：第一层提示词强约束（"仅输出 JSON，不要输出任何其他内容"）；第二层 temperature 压到 0.2 降低随机性；第三层是独立的解析节点兜底。细节：兜底不是"报错重试"而是"降级给默认值 8 分 + 一般了解"，因为业务上一条线索降级进培育池的代价，远小于整个流程卡死让销售等不到结果。另外解析出来的分数我会再夹紧一次 0-30，防止模型返回 300 分这种越界值。

Q4怎么保证 AI 生成的话术不瞎编？

结论：不让它自由发挥，只让它"基于资料说话"，并明确允许它说不确定。理由：三段设计 —— 生成前先做知识库检索（3 份文档）、检索结果用 context 注入提示词、提示词里写明"资料未覆盖的功能点，明确写'需与产品团队确认'，禁止编造"。细节：我不会对客户说"绝无幻觉"，这是不诚实的。准确说法是"把输出约束在可验证的范围内"——涉及报价和功能的表述必须能回溯到知识库某一段。真上线还会加人审环节。

Q5成本怎么控制？一条线索大概花多少？

结论：靠"分支前置 + 分级调用"，不是靠省提示词。理由：每条线索必跑 2 次小模型调用（结构化提取 + 意图评分）；只有 SQL 线索再走 1 次向量检索 + 1 次话术生成，MQL 走 1 次培育生成；无效线索（约 77%）到分支就结束了。细节：具体金额取决于客户选哪个模型（我在 DSL 里默认用的是轻量模型 gpt-4o-mini，实际部署建议换成 DeepSeek 或私有模型进一步降本）。给客户算账时我会按"每月线索量 × 各等级占比"列一张表，而不是报一个笼统单价。

Q6为什么分级用 if-else 而不是让模型判断？

结论：确定性裁决不该交给概率模型。理由：阈值是业务规则，需要可审计、可回归测试、能被业务方改 —— 客户说"我们金融行业可以放宽到 55 分"，我改一个数字就生效，不需要重训模型、也不用重新评估准确率。细节：而且 if-else 是零成本的，如果让模型判分级，每天几百条线索全都要多花一次调用，这是纯粹的浪费。

Q7这个工作流现在能直接上线给客户用吗？还缺什么？

结论：不能，它是一份合格的 POC，离生产还有 4 件事。理由：① 缺真实数据回测（阈值未经校准）；② 缺 CRM 回写（现在结果只在 Dify 里，没回流到客户客户档案）；③ 缺评分申诉的界面和留痕；④ 缺监控告警（模型调用失败、兜底命中率没有观测）。细节：我把它定位成"需求验证原型"，价值在于让客户在两周内看到效果、把需求聊具体 —— 直接和生产环境绑定反而是不负责任的。

Q8怎么评估这套评分到底有没有效？

结论：分两层指标，POC 期看一致率，上线后看成交率。理由：POC 阶段用双盲对比 —— 让 AI 和资深销售各自独立给同一批线索分级，一致率 ≥80% 才允许上线；上线后真正的指标是 SQL 线索的成交转化率有没有提升。细节：为什么先看一致率？因为销售如果发现 AI 判断和他们的直觉差太多，系统再准也不会被使用。先让系统"和专家对齐"，再谈"比专家更好"。

Q9如果客户要用自己现有的 CRM，怎么接？

结论：通过 API 做双向对接，不需要改客户的 CRM 逻辑。理由：Dify 工作流可以发布成 API/Webhook —— 客户 CRM 里的表单提交、或埋点事件触发时调一次，把返回的各项分数和话术写回客户档案对应字段。细节：真正的工作量不在技术，而在字段映射和确认：客户的 CRM 里"岗位"是什么枚举值、"行为轨迹"有没有存 —— 这一步通常要跟客户的销售运营一起过一遍，这也是售前该做的事。

Q10知识库为什么是这 3 份文档？检索参数为什么是 top_k=3？

结论：3 份文档覆盖售前最常被问的三类问题，top_k=3 是 POC 的成本与信息量折中。理由：《产品功能手册》答"能不能做到"、《常见问题 FAQ》管报价口径和数据安全这类高频问题、《客户案例集》提供同行业背书 —— 正好对应销售被问崩的三个场景。细节：分片和 rerank 我故意在 POC 里关了，是为了简化变量、先跑通主链路；生产环境我会打开 rerank 并做分片调优，因为脏文档切得太碎反而会拉低检索质量。

Q11为什么不同节点的温度不一样？

结论：任务性质决定温度 —— 要确定性就压到 0.2，要人味就放到 0.4-0.5。理由：结构化提取和意图评分必须可复现（同一条留言两次跑出来的分数不能不一样，否则销售会质疑），所以 0.2；跟进话术需要自然流畅但不能跑偏，0.4；培育文案希望有变化、不千篇一律，0.5。细节：这种"同一工作流里按节点调参"的细节，其实反映了我对每个节点职责的定位 —— 温度不是统一设一个默认值就完事的。

Q12这个项目里你具体做了什么？

结论：需求拆解 + 工作流搭建 + 交付文档，三件事都是我自己做的；需求访谈的对象是模拟的（这是求职作品集的定位，我会主动说明）。理由：需求拆解是把"能不能让 AI 先帮我们看一遍线索"这种模糊诉求，翻译成输入字段、输出格式、流程节点和验收标准；搭建是在 Dify/Coze 上把 13 个节点的提示词、代码、变量绑定全部跑通，并做了 3 条测试用例验证。细节：另外我做了配套的 Python 批量脚本（读 Excel 批量生成跟进消息）、300 条模拟商机的数据分析（用统计结果反过来验证"岗位比规模更关键""下载白皮书是弱信号"这些权重假设是否站得住）。我不会夸大成"生产上线项目"——它是一个完整闭环的 POC。

六、我发现的 4 个待改点

面试里主动说出这些，比背诵"我做得很好"更有杀伤力 —— 它证明你真正读懂了这条工作流，而不是复制粘贴了一个模板。而且这些改动都在 10 分钟内能做完，建议演示前就改掉。

待改点 1｜两份文档的"行为分"口径不一致（演示前必须修）

Dify导入说明.md 里写的是"预约演示 12 / 试用注册 9 / 浏览价格页 8"，但 DSL 里 rules 节点的代码实际是"打开报价邮件 15 / 预约产品演示 15 / 观看演示视频 12 / 访问集成对接页 10 / 一周内多次访问官网 10 / 下载白皮书 8"。两套完全对不上。

风险：客户或面试官把说明文档和画布一对照，立刻能看出来 —— 这比说错一个数字更伤，因为它怀疑的是严谨性。改法：把 Dify导入说明.md 的评分口径改成与代码一致，或者反过来把代码改成文档里的那套（推荐前者，代码里的行为项更丰富、更贴合 B2B 场景）。

待改点 2｜提取节点的 JSON 没被解析，被当成"核心诉求"直接喂给了下游

advice 节点里写的 核心诉求：{{#extract.text#}} —— 而 extract.text 是模型输出的整段 JSON 字符串（形如 {"need_summary":"...","need_keywords":[...],"contact":"..."}），不是干净的"核心诉求"。

影响：模型每次都要多绕一层去理解这段 JSON，既浪费 token 又可能理解偏；而且 JSON 里还夹带 contact 联系方式，等于把无关信息混进了提示词。改法：在 extract 之后加一个极短的代码节点（或直接把 extract 节点改成结构化输出），解析出 need_summary 和 need_keywords 再往下传，提示词里就写 {{#parse_extract.need_summary#}}。这是最能体现工程细节的一处优化。

待改点 3｜兜底是"静默"的，出了问题你不知道

parse_intent 解析失败时只返回默认 8 分，没有任何标记。也就是说模型连续 100 次输出格式错误，整个系统会安静地给 100 条线索打 8 分，永远不会有人发现。

改法：给兜底返回加一个 is_fallback: true 字段并打到输出里（或写日志），配合监控看"兜底命中率"。这个指标直接反映模型可用性，是生产环境必备的可观测性设计。

待改点 4｜"无效线索不进付费 LLM 节点"这句话说过头了

README 和案例文档里都写了"条件分支前置，无效线索不进付费 LLM 节点"。但严格说，无效线索已经跑过了 extract 和 intent_llm 两次大模型调用 —— 省掉的只是知识库检索和话术/培育生成。

改法：把表述改成"无效线索不触发知识库检索与话术生成，省下最贵的一段"。为什么这个点重要：如果在面试里把成本优势说过头，被追问"那提取和意图评分不是也调了模型吗"，就是当场翻车。精确 > 好听。

七、面试前 10 分钟自测清单

逐条自问，能不看稿讲出来就算过关。任何一条卡住，回去翻对应章节。

  • 能用一句话说清这个工作流解决什么问题（不出现"节点""编排"这类词）
  • 能报出 13 个节点的名字和顺序，并说清每个节点一句话的作用
  • 能解释为什么属性和行为用代码算、只有意图用大模型
  • 能背出三段评分的满分值（45 / 25 / 30）和两条阈值（60 / 30）
  • 能说出三条支线各自触发什么动作（检索+话术 / 培育 / 归档）
  • 能解释"解析兜底"节点存在的意义，并说出兜底值是多少（8 分 / 一般了解）
  • 能说出 RAG 防幻觉的三段设计，并诚实地说"不承诺零幻觉，只承诺可追溯"
  • 能回答"60/30 怎么来的"，并给出回测校准的方法（不粉饰"这是初始值"）
  • 能说出五条边界中最关键的两条（阈值需校准、幻觉边界）
  • 能主动讲出至少两个待改点，并说清为什么（口径不一致 / JSON 未解析 / 兜底无观测）
  • 能当场演示三条用例并解释分差（SQL 72 分 vs MQL 45 分 vs 无效 12 分）
  • 能诚实定位项目性质：完整闭环的 POC，不是生产上线项目

最后一句提醒

这份工作流最大的说服力不在"AI"两个字，而在每个设计都能说出理由：为什么这么分维度、为什么这么定阈值、为什么这里用代码那里用模型、哪些地方还不够好。面试官招的是"能把客户需求翻译成技术方案的人"，不是"会点按钮的人"—— 你把这 13 个节点的每一个"为什么"都讲清楚，就已经超过大多数候选人了。

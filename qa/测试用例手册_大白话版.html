依据：Dify导入_AI-CRM线索评分助手.yml 真实评分规则推算预期值 ｜ 18 条即用用例 ｜ 2026-09-28

先把一句话记住

传统代码是"钥匙配锁"—— 插进去能开就是对的，测一次就够。AI 工作流是"老中医开方"—— 同一个病人今天和明天开的方子可能不一样。所以给 AI 写测试，不能测"对不对"，只能测"在不在合理范围内"。

一、为什么 AI 项目必须写用例（三个理由，都很现实）

打个比方

AI 工作流像一个刚入职的实习生。你花了半天教他规矩（写提示词），但他有几个特点：记性看运气（模型有随机性）、心情影响输出（温度参数）、偶尔自作主张（幻觉）。

怎么知道他能不能上岗？给他 20 道题，看对了多少道。这 20 道题就是测试用例 —— 而且这 20 道题以后每次你改动他（改提示词、换模型、调权重）都要重考一遍，看他有没有变笨。

理由大白话解释不用例会怎样
① 上线有门槛你得有个客观标准说"这版能用了"。不然"我觉得差不多了"是说服不了客户和自己的。上线后靠运气，客户第一条测试就翻车。
② 改动不退化你今天为了修 A 问题改了提示词，很可能把原来好的 B 弄坏了 —— 除非你把所有用例重跑一遍。越改越差，修一个漏三个，最后不敢动。
③ 演示有保底客户现场演示最怕翻车。用例就是你的"安全牌堆"—— 提前跑过 20 遍的输入，现场必稳。现场演示撞上模型抽风，尴尬到无法收场。

二、一条用例的五个要素（照这个模板抄）

很多人写用例只写"输入"和"简单期望"，所以判卷时只能靠感觉。一条合格的用例必须有这五样：

要素要求以你的项目举例
① 用例编号唯一、有规律（含层次）TC-01（正常）、TC-07（边界）、TC-13（异常）
② 输入6 个字段全部写具体值，不含糊制造业 / 500 人以上 / IT 负责人 / 打开报价邮件、访问集成对接页 / 留言"旧 CRM 想嵌 AI 评分，支持 API 对接吗？"
③ 预期结果必须可判定：等级 + 分数区间 + 关键内容都要给等级 SQL；总分 85-95；意图标签 集成需求；话术必须出现"API"或"集成"
④ 判定标准什么算通过、什么算失败，写死等级一致 且 分数在区间内 且 话术含关键词 → 通过；任一项不满足 → 失败
⑤ 设计理由这条在测什么能力（面试也爱问）验证"集成/API"这条最高档意图评分有没有真的生效

最容易犯的错：预期结果写"分数合理""话术质量好"

这种写法的用例等于没写 —— 判卷时你说不清算不算过。正确做法：把"合理"翻译成数字和关键词。比如"话术质量好"→"话术必须包含客户留言里的原词，且四段小标题齐全，且不出现'需与产品团队确认'（因为该问题知识库里有答案）"。

为什么不能要求分数一模一样？因为大模型有波动。判卷要像判作文 —— 不能要求一字不差，但可以要求"论点齐全、不跑题、字数达标"。分数线就用区间表示。

三、用例要分三层（只写第一层的人，一上线就出事）

第一层 · 正常用例
证明"能用"
每种结果至少 2 条：SQL、MQL、无效各来两条。这是地基。
例：IT 负责人问"支持 API 对接吗" → 必须判 SQL
第二层 · 边界用例
证明"分得准"
专门造卡在 60 / 30 分数线上的线索，看会不会判错级、封顶有没有失效。
例：总分 59 和 61 的两条 → 必须落在不同等级
第三层 · 异常用例
证明"崩不了"
空留言、超长留言、行为全空、模型返回乱码、中英混杂。
例：留言只写"你好" → 流程必须走完、不许报错

为什么边界用例最重要？

因为 bug 都藏在"差一点"的地方。一条 90 分的线索被判成 SQL，谁都不会觉得有问题；但一条刚好 60 分的线索，会因为意图分模型多给 1 分就跨级 —— 而客户最关心的恰恰是这条线划得准不准（"为什么这条你说值得跟？"）。正常用例是及格线，边界用例才是区分度。

四、怎么测：6 步操作（在 Dify 里手的动作）

1

先跑三条预置用例，确认链路是通的

SQL（≥60）/ MQL（30-59）/ 无效（<30）各一条。这一步只是验证"没接错线、模型都绑好了"，别急着看分数准不准。

2

单节点测：出问题时定位到具体节点

Dify 里每个节点都可以单独运行。把上一步的真实输出粘进去，单独跑 intent_llm 或 rules，看它自己这一环对不对 —— 能单点定位，才不会一改就全乱。

3

整条流跑：从输入到结束看完整输出

输入 6 个字段，等结果。重点看四个值：total_score、grade、intent_tag、以及中间节点暴露的 attribute_detail / behavior_detail（你的规则节点很给力，明细直接能看）。

4

逐条填记录表：算通过率

把每条用例的实际输出填进《测试记录表》，通过率 = 通过条数 ÷ 总条数。18 条里必须全过才算这版可用（关键用例 TC-01、TC-05 一条都不许错）。

5

抖动测试：同一条跑 3 次，看波动

这是 AI 项目特有的。同一条用例连跑 3 遍，如果总分差超过 ±5 分，说明温度太高或提示词档位不够清晰 —— 这一步能提前发现"客户现场重跑一次结果变了"的尴尬。

6

每次改动后回归：把 18 条全部重跑

改完提示词、权重、阈值、模型，都要重跑一遍并和上次的结果对比。这是防止"改一个坏一个"的唯一办法。

通过标准（可以直接写进验收文档）

指标标准为什么这么定
等级判定一致率≥ 80%（AI vs 人工双盲）POC 期最实用的指标 —— 销售认不认可比数学上的准确率更重要
关键用例通过率TC-01（SQL）、TC-05（无效）100%这两类是业务命门：漏掉高价值客户 / 放行垃圾线索，代价最大
分数抖动同一条跑 3 次，极差 ≤ ±5 分分数飘忽销售就不信，可解释性直接崩掉
兜底命中率≤ 5%兜底太多说明提示词约束不够，或模型能力不足
单条处理耗时≤ 30 秒对齐你案例文档里的验收标准（30 秒内完成打分）
数值边界不越界属性分 0-45、行为分 0-25、意图分 0-30防止封顶 / 夹紧逻辑失效导致总分爆表

五、测出来不对怎么办：先归因，再动手

新手最常见的错误是：结果不对 → 直接改提示词 → 结果还是不对 → 再改 → 越改越乱。正确顺序是往上游找，"错在哪一环"先定下来。

等级判错了？按这四条路查（从上往下，从代码到模型）

  1. 属性分不对 → 查代码，别查模型。用户能选的选项和 rules 里的字典键是否逐字一致？比如选项是"学生个人"、字典键是"学生个人"（这条你写对了）；但如果哪次改成"学生"，就会走默认值，分数全变。这一层是纯代码问题，改代码 5 秒钟解决，改提示词一辈子也解决不了。
  2. 行为分是 0 → 行为词没命中字典。客户填"预约演示"，字典里写的是"预约产品演示" → 切词后匹配不上，直接计 0。这就是为什么我在用例里专门放了一条 TC-11 去故意触发这个不匹配 —— 这类问题不测永远发现不了。
  3. 意图分忽高忽低 → 先看提取，再收档位。先确认 extract 有没有把诉求提取对（提取错了，评分再准也没用）；然后收紧提示词里的六档评分标准（写得更细、每档给一个例句），并把温度压到 0.2。
  4. 走了兜底 8 分 → 模型没按 JSON 格式返回。在提示词里补一个"标准输出示例"（让模型照抄格式），同时给兜底加一个标记字段 is_fallback，方便统计命中率 —— 不然它静默兜底你永远不知道。
再打个比方

调 AI 工作流像医生调药：一次只动一味药。你同时改了提示词、又调了权重、又换了模型，结果变好了 —— 你不知道是哪一味起了作用，下次再出问题你就抓瞎了。

所以纪律是：一次只改一个变量 → 重跑全部用例 → 记录结果。改对了就留下，改错了就退回去。这样每一步都有据可查，面试时你还能讲出"我是怎么一步步把准确率从 60% 调到 85% 的"—— 这比说"我调了调提示词"强一百倍。

优化动作清单（对症下药）

症状可能原因对应动作
分数普遍偏低 / 高意向被判 MQL阈值定得太保守，或缺行为数据先用真实成交样本回测改阈值；确认客户能否提供行为字段（缺行为分就只有 75 分的上限）

七、面试怎么讲这套测试方法（三句话版本）

被问到"你怎么验证这个 AI 工作流是对的"

"我写了 18 条用例，分三层。第一层正常用例，SQL、MQL、无效各两条，保证基本能力；第二层边界用例，专门造卡在 60 分和 30 分线上的线索，还有验证封顶逻辑的极端输入 —— 因为 bug 都藏在差一点的地方；第三层异常用例，空留言、2000 字长文本、模型返回乱码，验证流程不会崩。"

"另外因为 AI 有随机性，我不测'分数完全一致'，而是测'等级一致 + 分数在区间 + 关键内容命中'。同一条线索连跑 3 次，极差要在 ±5 分以内。"

"最有用的是 TC-11，我故意填了一个字典里没有的行为词，结果行为分算成 0 —— 一下就暴露出输入选项和代码字典可能不一致的风险。这类问题是靠设计用例主动挖出来的，不测永远发现不了。"

被问到"测出问题你怎么改"

"我先归因再动手，不直接改提示词。因为分数 = 属性分 + 行为分 + 意图分，哪一段不对就查那一段的源头：属性分和行为分不对，一定是代码字典和输入枚举对不上，改代码；意图分不稳，先看提取对不对，再收紧评分档位、压温度；如果走了兜底，是模型没按 JSON 输出，我就在提示词里补一个标准输出示例。"

"而且我改的时候一次只动一个变量，改完把 18 条用例全部重跑，跟上一版结果对比 —— 这样才知道是哪一处改动起了作用，也能防止修一个坏一个。"

被问到"这套东西上线要看什么指标"

"POC 阶段看等级一致率，AI 分级和资深销售双盲对比，≥80% 才允许上线；另外两条硬指标是分数抖动 ≤±5 分、兜底命中率 ≤5%。上线之后真正看的是 SQL 线索的成交转化率有没有提升。"

八、动手前的自测清单

  • 能说出为什么 AI 项目不能像传统代码那样"测一次就够"
  • 能背出一条用例的五个要素（编号 / 输入 / 预期 / 判定标准 / 设计理由）
  • 能解释为什么预期结果要写成"区间 + 等级 + 关键内容"而不是一个精确分数
  • 能说清三层用例各自证明什么，以及为什么边界用例最重要
  • 能说出同一条线索跑 3 次、极差要控制在多少（±5 分）
  • 知道去 Dify 哪里单节点运行、哪里看中间节点的明细输出
  • 能背出归因顺序：先属性分和行为分（查代码），再意图分（查提示词），最后兜底（查格式）
  • 能解释"一次只改一个变量"的道理，并说得出你自己踩过的例子
  • 能说出至少两个数值边界（属性分 0-45、行为分 0-25）并知道为什么要测
  • 能当场说出 TC-11 这条用例的设计意图（故意制造字典不匹配）
  • 能说出通过标准里的两条硬指标（一致率 ≥80%、抖动 ≤±5 分）
  • 18 条用例里，能挑出你认为最重要的 3 条并说明理由

最后一句

测试用例这件事，本质不是"证明我的系统没问题"，而是"在客户发现之前，自己先发现问题"。你把 18 条用例跑通、把两个失败案例的归因过程讲出来，面试官听到的就不是"我做了个 AI 项目"，而是"这个人知道怎么把 AI 项目做扎实"—— 这两句话在评估表上不是一个档次。
